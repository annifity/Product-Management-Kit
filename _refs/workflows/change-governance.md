# Change Governance

1. Identify baseline artifact and approved scope.
2. Capture requested change and source.
3. Classify severity: minor, material, or breaking.
4. Ask for explicit PO accept/reject before code or committed docs change.
5. Assess impact on requirements, stories, UAT, Jira tickets, Confluence pages, timeline, dependencies, roadmap, and release notes.
6. Assess security, privacy, accessibility, AI-risk, and operational impact when the change touches data, permissions, user-facing behavior, or launch readiness.
7. Name decision maker, approver, consulted stakeholders, informed stakeholders, and accepted-risk owner.
8. Apply surgical edits only to affected sections unless a full rewrite is explicitly needed.
9. Append changelog rows; do not rewrite history.
10. Generate a spec change context block for developers and AI coding tools when implementation is active.
11. Notify affected stakeholders only after docs are verified.
12. Save final decision in docs and memories.

Breaking changes require PO, tech lead, and delivery owner alignment before execution.
